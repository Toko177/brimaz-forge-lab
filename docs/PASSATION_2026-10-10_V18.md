changements majeurs rapidement, et une **passation GitHub systématique**

## 3. Une amélioration opérationnelle majeure : lancer le simulateur

Un workflow **workflow_dispatch** est désormais créé sur `main` :
`.github/workflows/commander-four-ai-simulator.yml`.

Guide sur `main` :
https://github.com/Toko177/brimaz-forge-lab/blob/main/docs/HOW_TO_RUN_FOUR_AI_SIMULATOR.md

Dans GitHub → Actions → « Commander simulator — run 4 AI games »,
paramètres :
- branche `source_ref` : V18 actuellement ; récupérer sa dernière
  référence depuis `NEXT_CHAT_START_HERE.md` ;
- `pod=both` pour les deux groupes d'adversaires ;
- `policy=v17_strict` par défaut ; possibilité de v15, v16,
  v17_proactive sans changer le code ;
- `games_per_rotation=1,2,3,5` ;
- `seed_base` entier pour reproduire la matrice.

`both` avec 2 games/rotation exécute **16 vrais processus Forge**,
répartis en **8 jobs** parallèles, avec tous les sièges 0..3.
Toutes les sessions utilisent les mêmes decks canoniques déjà
vérifiés SHA256. Le workflow archive les logs, manifestes, décisions
par IA, empreintes des JAR et SHA du commit. Pas d'Oracle alternatif,
ni de cartes synthétiques.

**IMPORTANT :** le workflow de lancement manuel est installé sur main
et sa définition est vérifiée dans GitHub ; il n'a PAS encore été
exécuté par l'interface manuelle dans cette session. Vérifier les
premiers runs avant de présenter son débit comme mesuré. Un run futur
est une action volontaire de l'utilisateur, pas une tâche de fond
automatique.

## 4. Relecture par IA des vraies parties : V18

Nouveaux modules :
- `scripts/forensic_four_seat.py` : parse les événements réels
  Forge pour chaque joueur, tour et graine. Traces : terrains,
  sorts, activations, déclenchements, attaques déclarées,
  blessures de combat et poison reçus, blessure infligée attribuable,
  changements de points de vie, lenteurs de décision, réserve,
  pertes de Brimaz et rotations. JSON détaillé + Markdown lisible.
- `scripts/assess_simulator_readiness.py` : **garde de
  fonctionnement exploratoire**, distinct des trois critères
  « IA experte », « fidélité Oracle » et « winrate certifié ».
- `tests/test_forensic_four_seat.py` : fixture **synthétique étiquetée**,
  JAMAIS comptée comme une vraie partie.
- `tests/test_assess_simulator_readiness.py` : refuse les faux gains
  tirés de parties censurées / logs incomplets / sièges inactifs.
- CI `.github/workflows/four-ai-v18-forensics.yml` :
  télécharge **les 4 artefacts du vrai run V17 38081333961**,
  exige 8 logs / 4 matrices de pods/rotations, teste les parseurs,
  audite les quatre IA et conserve les résultats.

## 5. Résultats réellement observés et priorité de qualité

Sur ces **8 exécutions réelles** :
- Brimaz a lancé **119 sorts**, dont **24 lancements de son commandant** ;
- a déclaré **13 événements d'attaque**, infligé **87 blessures de
  combat connues aux joueurs** et en a reçu **389** ;
- **26 activations d'Incubateurs** ont été correctement identifiées
  sur les huit logs, contre une valeur fausse de 0 dans la première
  version du parseur (corrigée par 7cfd3850 et régression b346ad2a) ;
- n'a gagné aucune des huit exécutions ; ne pas inférer un taux
  statistique de victoire indépendant à partir de quatre graines appariées.

L'hypothèse prioritaire est **la survie et la pression offensive de
Brimaz par rapport à ses trois opposants**, MAIS ces statistiques ne
prouvent aucune action illégale manquée ni qu'un lancer de commandant
était mauvais. Mesurer les choix disponibles et la valeur des réponses
adverses avant de réécrire aveuglément l'heuristique.

Les tests V17.1 précédents (run 38082154931) sont maintenant
**SUCCESS dans les quatre jobs, huit parties naturelles**. Un seul
bloqueur fut retenu par le mode de défense anticipée (pod aristocrates,
rotation 1), sans changement de gagnant. Pas de gain de niveau démontré.

## 6. Remise en question / tâches de développement majeures

1. **Interventions adverses :** instrumenter les choix Forge réellement
   légaux sur la pile et les réponses des trois joueurs (priorité APNAP,
   informations cachées protégées) ; ensuite comparer les politiques
   alternatives à état public égal. Le source upstream Forge possède
   des TODO multi-opposants dans `GameSimulator` : ne pas activer
   `USE_FULL_SIMULATION` comme si le multijoueur était garanti.
2. **Survie de Brimaz :** isoler les séquences cast →
   destruction/exil → coût de relance → perte de tempo et les causes
   réelles, puis tester une politique défensive sur des **positions
   Forge authentiques**, sans changer les règles ou la liste de cartes.
3. **Tournoi plus large :** démarrer via le lanceur main une campagne
   à 40 parties (5 par rotation et pod), puis conserver toutes les
   censures, logs et SHA. Avant de citer un vrai taux de victoire,
   utiliser `scripts/certify_commander_games.py` avec le rapport
   Scryfall de légalité, plus une incertitude statistique.
4. **Débit :** choisir d'abord la parallélisation des **parties JVM
   indépendantes** et les preuves JFR ; ne jamais ajouter un cache
   mutable global qui change les décisions ou les règles.
5. **Gameplay humain :** références Game Knights / The Command Zone et
   SOLRING déjà répertoriées, mais la collecte YouTube automatisée
   a été bloquée sur GitHub Actions. Ne pas prétendre disposer de
   trajectoires humaines complètes.
